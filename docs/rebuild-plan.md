# サイト再構築プラン — 「個人ツール」から「誰でも使えて競合より優位なサービス」へ

作成日: 2026-08-16
関連: [design.md](./design.md)（UI/UX刷新の詳細）, [implementation-status.md](./implementation-status.md), [checklist.md](./checklist.md)

## 0. エグゼクティブサマリー

現状の VRChat Avatar Watch は「開発者本人が使う分には十分」なレベルまで機能が揃っている（自動アバター判定、素体グルーピング、AND検索、Web Push、Discord/Misskey通知など）。しかし公開サービスとして競合（VRCFinder、よりみちクローゼット）と比べると次の3点で明確に劣っている。

1. **SEO実装が事実上ゼロ** — meta description / OGP / JSON-LD / sitemap.xml / robots.txt / 動的titleのいずれも未実装。検索流入という最大の集客チャネルを自ら塞いでいる。
2. **タグ・ジャンル体系が「BOOTHのセラータグをそのまま集計するだけ」** — 独自の横断軸（テイスト・体型・カラー・シーン・目的）が無く、競合の主力検索体験に見劣りする。
3. **拡張の入口が管理者一人に閉じている** — 新しいアバター/ショップをサイトに載せる手段が管理画面の手動登録しかなく、ユーザーが「このアバターも扱ってほしい」と言える経路が無い。「誰でも使える」の前提となる「誰でもサイトを育てられる」が欠けている。

一方で、**通知（お気に入り・監視・Web Push・Discord/Misskey）と自動クローラー基盤は他サイトより成熟している**。ここを核に据え、正面から物量（掲載点数）で戦うのではなく「見逃さない・自分ごと化できる」体験で差別化する方針とする。

## 1. 現行要件の要/不要判定

### 1.1 残す・そのまま活かす

| 機能 | 現状 | 判定理由 |
|---|---|---|
| BOOTH低頻度クロール基盤 (`app/crawler/booth.py`) | robots尊重、同時1接続、間隔制御 | 運営上の安全性が高く継続資産。効率化は§5で扱う |
| 自動アバター判定 (`avatar_service.py`) | キーワードルール＋疑わしい名前の検出 | 手動タグ付けなしで規模を出せる中核ロジック。精度向上は§6 |
| 素体（共通ボディ）グルーピング | 半自動検出＋管理者確定 | 競合にない独自軸。コミュニティ参加型に発展させる価値大（§6） |
| AND検索クエリ (`avatar:` `tag:` `free:true` 等) | Phase1/3で実装済み、入力補助UIあり | エンジンとしては競合と遜色ない。表出UIのみ弱い（§design.md） |
| お気に入り／アバター監視／ショップ監視 | 実装済み | 差別化の核。強化対象（§2.3） |
| Web Push／Discord Webhook／Misskey通知 | 実装済み、複数デバイス対応済み | 競合が持たない自社の強み。最優先で伸ばす |
| ランキング集計・無限スクロール・Questバッジ・お気に入りボタン | Phase1/2で実装済み | 継続。表示単位・期間の見直しのみ（§design.md） |
| PWA（manifest / offline fallback） | 実装済み | 継続 |

### 1.2 捨てる・整理する

| 対象 | 理由 |
|---|---|
| `app/crawler/scheduler.py`（APScheduler版） | どこからもimportされていない未使用のデッドコード。実際に動いているのは `app/services/scheduler.py` の threading ループ。混乱の元なので削除 |
| BOOTHライブラリの「手動HTML貼り付け」インポート | 個人利用前提のUX（HTMLソースを手でコピペ）。万人向けには成立しない。§2.3で代替案を提示 |
| `Item.category` のBOOTH文字列そのまま使い | 正規化されたジャンルマスタに置き換える（§6） |

### 1.3 変える（個人用 → 万人向け）

| 現状 | 変更方針 |
|---|---|
| クロール対象の追加は管理画面のみ | ユーザーからの「このアバター/ショップを追加リクエスト」受付＋簡易審査キューを新設（§2.3, §5） |
| ページtitleが全ページ固定 | 商品名・アバター名・タグ名を反映した動的title/meta生成に変更（§4） |
| タグ = BOOTHセラータグの集計のみ | 独自ファセット（テイスト/体型/カラー/シーン）を追加（§6） |
| 検索クエリ構文がパワーユーザー向け | 初見ユーザー向けにチェックボックス/チップUIを主導線化（クエリは上級者向けオプションに降格。§design.md） |
| 通知経路がDiscord/Misskey/Web Pushに限定 | 継続強化しつつ、まずは既存3経路の信頼性（複数デバイス、未送信の再送）を固める |

## 2. 競合調査と差別化方針

### 2.1 VRCFinder（https://vrcfinder.net/ja/）

- Gatsby製の静的サイト（SSG）。**SEOが極めて作り込まれている**: 動的description、OGP/Twitter Card完備、JSON-LD（Organization / WebSite / BreadcrumbList）、robots meta、canonical、Bing Webmaster検証タグまで設定済み。
- 収集数46,868件を前面に押し出す物量訴求。
- **独自タグ＆キーワード**でテイスト・体型・カラー軸の横断検索を提供（BOOTHタグの再分類・拡張をしている）。
- **季節特集ページ**（春/夏/秋/冬/ハロウィン/クリスマス/お正月）が常設リンクとして存在 — テーマ別ランディングページによる検索流入とロングテールSEOを狙った構成。
- **週次/月次トレンドレポート**をブログ記事として継続publish（「新作人気急上昇スナップショット」「人気ワールドランキングTOP10」等）。これはコンテンツSEOであり、かつBOOTH商品説明ではなく編集された紹介文をアバターごとに書いている（AI/人力生成と思われる）。
- カテゴリ別ランキング、対応商品数の多い人気アバターの解説カード。

### 2.2 よりみちクローゼット（https://yorimichi.cc/ja）

- Next.js製（Cloudflareのbot対策あり、画像は独自リサイズAPIでWebP配信 = パフォーマンス最適化済み）。
- **「アバターを起点に探す」体験が主導線**: 自分のアバターを登録 →「対応アイテム」が自動で並ぶ。これは自サイトの `avatars/{slug}` に近いが、よりみちは「自分のクローゼット」というマイページ機能に統合している。
- **クローゼット機能**: 気に入ったアイテムを保存・整理し、他ユーザーの「みんなのクローゼット」「みんなの着こなし」を閲覧できるソーシャル要素（いいね、投稿）。
- **急上昇ランキング**を1日/7日/30日の期間別に用意し、「スキ増加数」という差分指標で「今の勢い」を見せる。
- **目的から探すタイル**（Quest対応／Modular Avatar対応／無料／セール中）をトップの主要導線に配置。
- **コミュニティ参加型の「アバターグループ補完プロジェクト」**（共通素体グループ登録をユーザーに手伝ってもらう）— 運営だけでなくユーザーがデータ整備に参加する仕組み。
- BETAを明示し「頻繁に変わる」ことを許容する期待値調整。

### 2.3 差別化方針（自サイトが取るべきポジション）

物量（掲載点数）と作り込みの両面で先行2社に単純比較で勝つのは非現実的。**「見逃さない」×「参加できる」**の2軸で独自ポジションを取る。

1. **通知特化の深掘り（最大の強み）**
   - 既存のお気に入り/監視/Web Push/Discord/Misskeyをさらに伸ばす: 価格変動アラート、セール開始/終了アラート、在庫・割引率アラート、新作即時通知。
   - 「急上昇ランキング」（よりみち型、1日/7日/30日のスキ・閲覧増分）を追加し、ランキング入りしたお気に入りアバターへの通知に接続する（"見ているアバターが急上昇したら教えて"）。
   - 通知チャンネルの選択肢をユーザーが自由に組み合わせられる設計（既に複数デバイスWeb Push対応済みなのでここは仕上げの領域）。

2. **ユーザー参加型のカバレッジ拡大（管理者一極集中からの脱却）**
   - 「このアバター/ショップを追加してほしい」ボタン → 追加リクエストキュー → 自動クロール試行＋簡易審査 → 反映、のフローを新設。これは§1.3・§5と直結。
   - 素体グルーピングやタグ付けの「ユーザー投票/提案」機能（よりみちの「アバターグループ補完プロジェクト」に相当）。人手を借りて自動判定の精度を上げる仕組み自体を差別化要因にする。
   - BOOTHライブラリの手動貼り付けインポートは廃止し、Discord連携済みユーザーであれば「お気に入りアバター登録」だけで完結する導線に置き換える。

3. **SEOでの基礎体力の確保（差別化ではなく必須の追いつき）**
   - VRCFinder相当の基本実装（title/description/OGP/JSON-LD/sitemap/robots）を最優先で追いつく。詳細は§4。
   - コンテンツSEO（季節特集・トレンド記事）は工数が大きいため、Phase2以降の投資判断とする（自動生成の可否を含め要検討）。

4. **タグ軸の拡張**
   - VRCFinder型の「テイスト/体型/カラー」ファセットとよりみち型の「目的（Quest対応/MA対応/無料/セール）」タイルの両方を採用し、既存の自動判定ロジック（`detection.py` のブールフラグ）を土台に拡張する。詳細は§6。

## 4. SEO対策

### 4.1 現状

`app/templates/base.html` の `<title>` はサイト名固定、meta description/OGP/JSON-LD/canonical/robots.txtいずれも未実装。`app/main.py` に `sitemap.xml` や `robots.txt` の配信ルートも無い。

### 4.2 対応方針（優先度順）

1. **`robots.txt` 配信ルートを追加**（`/robots.txt`）— 全ページ許可＋ `Sitemap:` 行でsitemap.xmlを案内。
2. **`sitemap.xml` の動的生成**（`/sitemap.xml`、件数次第で `sitemap-items-N.xml` にインデックス分割）— 対象: トップ / 検索カテゴリページ（sales, free, tools） / アバター一覧・詳細 / 素体一覧・詳細 / 商品詳細 / タグ別ページ（§6で新設）。更新頻度の高い商品詳細は `lastmod` にクロール更新日時を反映。
3. **`base.html` のtitle/meta description をブロック化しページごとに上書き可能にする**。
   - 商品詳細: `{{ item.title }} | {{ avatar_names }}対応 | {{ site_name }}`
   - アバター詳細: `{{ avatar.name }}対応アイテム一覧 | {{ site_name }}`
   - タグ/カテゴリページ: `{{ tag }}のVRChatアイテム一覧 | {{ site_name }}`
   - description は商品説明の冒頭やアバター対応商品数などから自動生成。
4. **OGP / Twitter Card**: 商品画像・アバターサムネイルを `og:image` に設定。デフォルトOGP画像も1枚用意。
5. **JSON-LD構造化データ**:
   - 共通: `Organization` / `WebSite`（サイト内検索の `SearchAction` を含める）
   - 商品詳細: `Product`（`offers.price`, `image`, `aggregateRating` は無理に付けない＝Google側のリッチリザルト誤検出リスクを避ける）
   - 一覧系: `BreadcrumbList`
6. **canonical URL**: `sort=` `offset=` などクエリパラメータ違いの重複ページを正規化。無限スクロールで生成される部分HTML（`hx-*` レスポンス）はnoindexにするか、そもそも検索エンジンにクロールさせない（`/api/*` や部分テンプレートへの直リンクを避ける設計にする）。
7. **内部リンク強化**: 商品詳細→対応アバター→同素体の兄弟アバター→関連タグ、という回遊導線をSEO文脈でも強化（クローラーの巡回性向上に直結）。
8. **Search Console / Bing Webmaster Tools登録**、`msvalidate.01` 相当の検証タグ設置。
9. （Phase2以降）コンテンツSEO: 週次/月次トレンド記事や季節特集ページ。工数対効果を見て判断。

## 5. クロールの効率化

### 5.1 現状の課題（Explore調査より）

- `app/crawler/scheduler.py`（APScheduler版）が未使用のまま残存し、実際は `app/services/scheduler.py` のthreadingループが稼働 — 二重実装で保守性を損なっている。
- `CRAWL_WRITE_LOCK` によりクロール処理全体がプロセス内で事実上シリアル実行。過去の重複キー/デッドロック障害（2026-07-13、`docs/checklist.md`記載）への対処として導入されたが、対象数が増えるほどスケジューラ1周の所要時間が線形に伸びる。
- 商品詳細ページの補完取得が「閲覧のたびに `SessionLocal()` を新規生成してBOOTHへ取得しに行く」設計（`public.py` の `_run_item_detail_fetch`）— アクセス集中時にBOOTHへのリクエストが増える可能性。
- `avatar_service.ensure_avatar_page_for_item` のアバター名重複チェックが商品ごとに個別クエリを発行しており、大量クロール時にN+1になりうる。

### 5.2 対応方針

1. **デッドコード削除**: `app/crawler/scheduler.py` を削除し、稼働中の実装（`app/services/scheduler.py`）に一本化。ドキュメントも合わせて更新。
2. **書き込みロックの粒度を見直す**: プロセス全体の直列化ではなく、クロール対象（ショップ/キーワード）単位や、Item/Avatar作成のトランザクション単位でロック範囲を絞る。まずは現状のログから実際のボトルネック（対象数×平均処理時間）を計測してから設計する。
3. **詳細補完取得の重複排除**: 同一商品への同時アクセスに対する取得中フラグ／キャッシュ有効期限を明確化し、「閲覧ごとに毎回BOOTHへ取得しにいく」状態を避ける（例: 直近取得成功から一定時間はスキップ）。
4. **アバター名重複チェックの一括化**: クロールバッチ開始時に既存アバター名を一括ロードしてメモリ上で照合する（既存の `_avatar_match_index` の仕組みをアバター新規作成判定にも適用）。
5. **優先度付きクロールキュー**: §2.3のユーザー追加リクエストを、通常の定期クロールとは別の優先レーンとして扱い、リクエストから反映までの体感時間を短縮する。
6. **差分駆動の詳細再取得**: 一覧クロールで検知した価格・在庫・タイトル変化がある商品のみ詳細補完を優先し、変化のない商品の再取得間隔を延ばす（BOOTHへの負荷軽減にも直結、現行の低頻度方針と整合）。
7. **クロールメトリクスの可視化**: 失敗率・平均所要時間・スキップ率を管理画面のダッシュボードに追加し、ボトルネック箇所を継続的に把握できるようにする。

## 6. ジャンル分け・タグの最適化

### 6.1 現状

- `Item.category` はBOOTHのカテゴリ文字列をそのまま保持。
- タグは `ItemTag`（BOOTHセラーが付けたタグの集計表示のみ）。独自の分類マスタは無い。
- 判定はブールフラグ群（`is_free` / `is_on_sale` / `is_tool` / `is_nsfw` / `is_quest_compatible`）で実装され、これ自体は目的別フィルタの土台として優秀。
- 階層は「Item ⇔ Avatar（多対多）→ BaseBody（Avatarのnullable FK）」の2段のみ。

### 6.2 対応方針

1. **正規化されたジャンルマスタの導入**: `Item.category`（BOOTH文字列）とは別に、サイト独自の大分類（アバター / 衣装 / 髪型 / アクセサリー / テクスチャ / ギミック・ツール / 小道具 / ワールド / アニメーション 等）へのマッピングテーブルを用意し、BOOTHのカテゴリ変更に左右されない安定した分類軸を持つ。
2. **既存ブールフラグの導線格上げ**: `is_quest_compatible` / `is_tool` / `is_free` / `is_on_sale` は既に判定済みなので、よりみち型の「目的から探す」タイルとしてトップページ・検索の主要導線に昇格させる（実装コスト低、効果大）。
3. **独自ファセットタグの追加**（VRCFinder型）: テイスト（量産型/地雷系/ゆめかわ/ゴシック/クール 等）・体型・カラーなどの横断軸を、既存の `ItemTag`（BOOTHセラータグ）からシノニム辞書・キーワードマッピングで自動分類する。手動タグ付けは運営コストが高いため、既存の自動判定思想（キーワードルール＋疑わしいものは人力レビュー）を踏襲する。
4. **タグの表記ゆれ統合**: 同義語・類似タグ（例:「猫耳」「ねこ耳」「ネコミミ」）を正規化するシノニムテーブルを導入し、タグクラウド・検索の双方に適用する。
5. **素体グルーピングの精度向上とコミュニティ参加**: `detect_base_body_candidates` による半自動検出は継続しつつ、ユーザーが「このアバターとこのアバターは同じ素体では」と提案できるUIを追加し、管理者承認フローに載せる（よりみちの「アバターグループ補完プロジェクト」相当）。
6. **タグ別ランディングページの新設**: 各独自ファセットタグ・大分類ごとに専用URL（`/tags/{slug}` 等）を用意し、§4のSEO施策（動的title/description、内部リンク）と接続する。

## 7. 実行ロードマップ（目安）

| フェーズ | 内容 | 依存関係 |
|---|---|---|
| Phase A（基礎体力） | SEO基本実装（§4の1〜7）、デッドコード削除（§5.1）、目的別フィルタの導線格上げ（§6.2） | 他フェーズより先行して着手可能、影響範囲が広くリスク低 |
| Phase B（差別化の核） | 通知強化（急上昇ランキング接続、アラート種別拡充）、ユーザー追加リクエストキュー（§2.3） | Phase Aのタグ/ジャンル整理が前提になる箇所あり |
| Phase C（データ整備の仕組み化） | 独自ファセットタグ、素体グルーピングのコミュニティ提案機能、タグ別ランディングページ | Phase A/Bのデータ基盤が前提 |
| Phase D（コンテンツSEO・任意） | 季節特集・トレンド記事 | 工数対効果を見て判断。自動生成の可否を検討 |

各フェーズの詳細な画面設計は [design.md](./design.md) を参照。
